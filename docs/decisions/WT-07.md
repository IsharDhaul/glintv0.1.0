# WT-07 decisions

- 2026-10-30: No module exposed a `Stage` yet, so the adapters live in `engine/glint/pipeline/stages.py`. Each one calls only its module's public functions (`download_bulk`, `extract_folder`, `write_companies`, `build_financials`, `ingest_dates`, `PriceStore.read_bars` + `adjust_for_splits` + `price_stats`). Stage order is the brief's, unchanged. `metrics` and `flags_quality` are `NotBuiltYet` stages that raise a clear error naming WT-06, so until WT-06 merges every full refresh stops there and publishes nothing.
- 2026-10-30: "Skip the SEC stages" means the sources haven't changed, not that the pipeline already ran today. `download_sec` always makes the conditional GETs (ETag / Last-Modified), which costs 3 requests, and reports SKIPPED when SEC answers 304 for every file. A time-of-day rule ("already downloaded today") would miss SEC's ~03:00 ET rebuild if the first run was earlier. `extract_facts` is SKIPPED when facts_raw's stamp matches the companyfacts sha256 and the tag-whitelist hash (WT-01's own stamp).
- 2026-10-30: companies.parquet is rebuilt only when its inputs change. A pipeline-owned stamp, `_companies.pipeline.json` next to it, records the submissions/tickers/companyfacts sha256s, a hash of the config files the universe reads, and a hash of `engine/glint/universe/*.py`. The table is loaded into every build either way. A parquet written by `glint ingest sec` has no stamp, so it is rebuilt once.
- 2026-10-30: `financials` always recomputes (brief step 4). Its coverage report (WT-03's definition: TTM flows, MRQ instants, default universe, per group) is stored as integer counts `coverage.<group>.<item>` and `coverage.<group>.companies` in that stage's `pipeline_runs.counts`. That keeps `StageResult.counts` as `dict[str, int]`, needs no contract change, and lets the next build compare against any earlier build file.
- 2026-10-30: A price-provider failure is a WARN, not an abort. SPEC §4.1 says it "never stops the screen running on fundamentals", which overrides the brief's "abort on any failure" for this stage. `--no-download` means no network at all (no SEC, no prices). `--skip-prices` skips only the fetch; `price_stats` is still computed from the bars on disk, and the build records `as_of_prices`.
- 2026-10-30: `price_stats` covers every ticker with bars (the whole market, ~14.8k), not just the universe, and reads only through `PriceStore.read_bars`. TCBI history therefore arrives as TXCP once a bar on or after 2026-11-09 is on disk (test: `test_price_stats_follow_ticker_changes`). Joining a renamed ticker back to a company is the metrics stage's job (WT-06). SEC still listed TCBI on 2026-10-29.
- 2026-10-30: `pipeline_runs` is written into the new build after **every** stage, so a killed run's file shows `running` plus the stages that finished. The final status (`ok`/`warn`) and the previous-build comparison are written *before* the pointer flips, because nothing writes to a build once the API can see it.
- 2026-10-30: Retention keeps the new build and the one it replaced (`KEEP_BUILDS = 2`). After a successful publish, every other file in `builds/` is deleted, including failed and killed runs. A failed build stays until then, for inspection. `user.duckdb` sits outside `builds/` and the pipeline never opens it: `connect_build` refuses that path, and a spy test checks every `duckdb.connect` call.
- 2026-10-30: `--only` / `--from` rerun stages on a **copy** of the current real build (never in place), and `publish` is added automatically when any selected stage writes the build. A missing or synthetic current build is an error that tells you to run a full refresh. Selecting only raw stages (e.g. `--only download_sec`) creates no build.
- 2026-10-30: Old SEC download folders are pruned after a successful publish (marker `companies.parquet`, WT-01's `prune`), so a folder is never removed before a build from its successor succeeded.
- 2026-10-30: `build_id` is the UTC start time as `YYYYMMDDTHHMMSSZ`, which sorts and is safe in filenames. Reports show UTC, London and New York times. `archive_snapshot` writes `snapshots/date=<UTC date of build_id>/`, and a second build on the same day replaces that day's archive.
- 2026-10-30: The coverage-drop threshold is `audit.coverage_drop_warn_pp` (0.02) in config/thresholds.yaml. It applies both to line-item coverage drops and to P0 null-rate rises. A breach makes the run `warn` and appears in the report and in `pipeline_runs.warnings`. It never blocks the publish.
- 2026-10-30: One `refresh.lock` per `GLINT_DB_DIR` stops two refreshes in one checkout. Raw writes take `raw.lock` per stage, not for the whole run, so other worktrees can read and write raw between stages.
- 2026-10-30: Removed the `refresh` row from the stub list in `engine/tests/test_cli.py` (WT-00's file; earlier worktrees removed theirs the same way). Once `glint refresh` was real, that test ran a full `--no-download` refresh against the real `~/GlintData/raw` and `./data`. That run is where the first real timings below come from. `engine/tests/pipeline/test_cli.py` now covers the CLI on temp dirs only.
- 2026-10-30: First real timings: a `--no-download` run on the 2026-10-29 SEC files and 300 price sessions, on a busy machine (pytest and pyright running in parallel). extract_facts 200 s (a real re-extract: concepts.yaml changed in WT-03), companies 40 s, **financials 631 s**, price_stats 1.3 s, then metrics failed (stub). Financials alone is over the §4.8 target of ≤ 5 min for a rebuild without downloading. That stage belongs to WT-03, so it's flagged here, not changed. To re-measure on a quiet machine.
- 2026-10-30: After WT-06 merged, the stage order became `download_sec → extract_facts → companies → financials → prices → price_stats → metrics → publish`. WT-06 exposes one `MetricsStage` that writes metrics_snapshot, metric_notes, metric_history **and** flags, and archives the snapshot to `snapshots/date=<as_of_fundamentals date>/` itself (WT-06 decision). So `flags_quality` and `archive_snapshot` no longer exist as separate stages. Running them separately would mean either reaching into WT-06's internals or archiving twice, under two different date keys. `glint audit` (quality) stays a separate command, not a stage. This replaces the `archive_snapshot` date rule in the `build_id` entry above.
- 2026-10-30: `MetricsStage` reads `as_of_fundamentals` / `as_of_prices` from `build_meta`, so the pipeline's `metrics` adapter writes build_meta first and `publish` writes it again before the swap. `MetricsStage` turns its own exceptions into a FAILED result. The adapter raises that message as `StageFailedError`, so the runner aborts the same way it does for every other stage, but the traceback stays inside WT-06 (the log gets the message only). Because the archive is written during `metrics`, a run that fails later (only `publish` remains) can leave an archive for a build that never went live. A rerun for the same date replaces it.
- 2026-10-30 (review fixes): A partial run (`--only`/`--from`) stays on the data its copied build was made from. `pipeline_runs.source_timestamps` now records `sec.folder`. A partial run that doesn't rerun `companies` reads the SEC folder from there instead of taking the newest one on disk. `as_of_prices` comes from the build's `max(price_stats.as_of)`, not the newest bar on disk. A partial run also carries the copied build's counts forward for the stages it doesn't rerun, so the next full run's coverage comparison still works. Builds made before this change have no `sec.folder` and fall back to the newest folder.
- 2026-10-30 (review fixes): Stage-level `raw.lock` waits up to 600 s (`RAW_LOCK_WAIT_S`), because another worktree's ingest shouldn't kill a 15-minute refresh. WT-06's `archive()` still takes the lock with no wait. That's a hand-off to WT-06, since the archive is their code. Once the pointer has flipped, pruning old builds and SEC folders can only add a notice (status `warn`, shown in the report and the console), never a failure. Those notices aren't in the build's `pipeline_runs`, because nothing writes to a build after it's live.
- 2026-10-30 (review fixes): The companies stamp now includes the parquet's own sha256. A `companies.parquet` rewritten by another checkout's `glint ingest sec` is rebuilt rather than reused. `financials` re-reads the parquet, and it fails with "rerun with --from companies" if the file changed after the companies stage loaded it. Stamps written before this change carry no sha, so they rebuild once.
- 2026-10-30: **Real timings** against SPEC §4.8, taken after WT-06 merged, on the 2026-10-30 SEC files with 301 price sessions:
  - **Cold full build: 797 s (13.3 min), target ≤ 30 min.** It downloaded companyfacts and submissions (2.99 GB) in 188 s, then extract 159 s, companies 26 s, financials 413 s, prices 1.5 s (one new date), price_stats 1.2 s, metrics 7.5 s, publish 0.1 s. Prices were backfilled already.
  - **Warm, same day: 482 s (8.0 min), target ≤ 10 min.** SEC answered 304 on every file (1.0 s), so extract was skipped. Companies was rebuilt once (29 s) because the cold run's stamp predated the parquet-sha fix; the next run reused it in 0.2 s. Financials took 443 s.
  - **`--no-download` in a fresh worktree** (empty `data/`, shared raw): published fine. Companies was reused in 0.2 s, financials took 480 s, metrics 8 s, and the stages total about 490 s (8.2 min). **That's over the ≤ 5 min target, and financials alone is 7–8 min.** Financials is WT-03's code, so this is a hand-off to WT-03 rather than a change here. The wall clock read 2,689 s because the Mac went into clamshell sleep 37 s into financials (`pmset -g log`, 18:51:32). Stage durations use the monotonic clock, which doesn't count sleep.
  - **Hand-off to WT-06:** a real build raises 8,305 flags over 8,023 companies, and metrics takes 7–8 s.
- 2026-10-30: **Live kill test** in that fresh worktree. `glint serve` ran on the published build, then `glint refresh --no-download` was SIGKILLed 2 s into `metrics` (metrics started 20:43:14.33, kill at 20:43:16). `current.json` was byte-identical afterwards, and the same API process kept serving the previous build: `/api/meta`, `/api/sectors` and `/api/companies/AAPL` all returned 200, during and after the kill. The killed build's `pipeline_runs` row reads `running`, with durations through price_stats. Its `metrics_snapshot` is empty, and the file sits in `builds/` until the next successful publish prunes it.
- 2026-10-30: The first real build exposed a bug. `pipeline_runs.source_timestamps` held SEC's raw HTTP dates, and `/api/meta` returned INTERNAL because the contract says datetimes. Every value is now ISO 8601, and the e2e test parses each one the way the API does.
- 2026-10-30 (review fixes): `--dry-run` now runs the partial-run checks (no real current build, or a schema mismatch). When `download_sec` would run, it marks `extract_facts` as "decided after download_sec" instead of guessing from today's folder.
- 2026-10-31 (pre-merge review): `--only` refuses a selection that would publish build tables computed from data it reran (e.g. `--only financials` without `metrics`); the error says to add them or use `--from`. Auto-adding them would make `--only` mean `--from`.
- 2026-10-31 (pre-merge review): non-`GlintError` exceptions between stages (recording, comparing) fail the run with a report instead of crashing as "interrupted"; any price-provider exception is a WARN (§4.1), not only `GlintError`.
- 2026-10-31 (pre-merge review): the price_stats session check uses WT-02's `DEFAULT_WINDOWS.required()` (253 today) instead of hard-coded 260/253; the companies stamp records the missing-submissions count so a reused parquet keeps its warning; a partial run whose pinned SEC folder was pruned fails with a clear message (WT-01's prune keeps the newest 3 folders and isn't changed here).
- 2026-10-31 (pre-merge review, not changed): the runner still names `download_sec`/`extract_facts`/`companies` in dry-run and `_inherit`. A stage hook would be cleaner, but it's three names in one owner's module; revisit if stages are renamed again.
- 2026-10-31 (pre-merge review, finding 7 follow-up): financials now holds `raw.lock` (waiting up to `RAW_LOCK_WAIT_S`) while it reads the SEC folder, so another worktree's post-publish prune can't delete a pinned folder mid-read. Cost: another worktree's ingest/prune waits for financials (~7 min on real data). The alternative, a `keep` set on WT-01's `prune()`, is outside WT-07's paths.
